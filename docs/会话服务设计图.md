# 会话服务设计图

本文用于重新定义 `conversation_service` 的职责边界，明确哪些能力应该暴露，哪些能力必须下沉或禁止暴露，避免再次出现“metadata 伪装成完整会话”导致的消息存储破坏。

## 零、第一原则

会话服务的第一原则：

**除显式批准的恢复/修复流程外，任何业务调用都不得拥有破坏既有会话消息历史的能力。**

展开后包含两条硬约束：

1. 只要接口边界设计正确，任何普通调用都无法破坏会话消息。
2. 项目内禁止任何业务代码绕过 `conversation_service` 直接读写会话消息仓库。

也就是说：

- 调用方只能表达业务意图，不能表达危险实现细节
- 普通路径不能直接操作 `blocks / index / manifest / meta` 文件
- 任何跨层直读直写都视为边界失守

唯一放开的口子：

- 只有“全量导入 / 全量导出同步 / 数据迁移恢复”三类特批流程，才允许覆写整个会话
- 这是为了迁移与外部数据同步，不属于普通业务写入能力
- 除这一例外外，所有正常路径都只能追加、受限替换、受限撤销、受限压缩

## 一、设计目标

会话服务只暴露业务意图，不暴露底层拼装细节。

核心目标：

1. 禁止“只有 meta 的对象”伪装成完整会话。
2. 禁止业务层直接调用带删块语义的底层重写能力。
3. 所有读取都必须明确区分“只读 metadata”与“读取完整消息”。
4. 所有写入都必须明确区分“只改 metadata”与“改动消息正文”。
5. 项目内所有会话消息相关读写都必须经由 `conversation_service` 暴露的受控接口完成。

## 二、错误设计（现状）

当前风险链路可以概括为：

```text
ConversationShardMeta
    └─ to_metadata_conversation()
          └─ 得到 Conversation { messages = [] }
                └─ 被后续代码误当成完整会话
                      └─ 参与 message_count / 持久化 / 全量重写判断
                            └─ 触发块文件误删
```

问题本质：

- `Conversation` 同时承担了“完整会话模型”和“metadata 投影模型”两种语义。
- `conversation_service` 暴露了不应该暴露的中间态能力。
- 上层调用方可以越过业务意图，误碰危险写盘路径。

## 三、正确设计（目标）

### 1. 三层模型

```text
+---------------------------+
| ConversationMeta         |
| 只含标题/状态/todo/goal  |
| 不含 messages            |
+---------------------------+
            |
            | hydrate
            v
+---------------------------+
| ConversationSnapshot     |
| meta + full messages     |
| 只能由服务层构造         |
+---------------------------+
            |
            | persist / append / truncate
            v
+---------------------------+
| MessageStore             |
| blocks / index / manifest|
| 不直接对业务层暴露       |
+---------------------------+
```

### 2. 分层职责

#### `ConversationMeta`

职责：

- 表达会话 metadata 的真实语义
- 可用于列表、筛选、状态判断、目标/待办读取
- 绝不能参与正文写盘

包含字段示例：

- `id`
- `title`
- `status`
- `summary`
- `conversation_kind`
- `unread_count`
- `current_todos`
- `active_goal`
- `preferred_api_config_id`
- `message_count`
- `preview_messages`

禁止：

- 不提供 `messages`
- 不允许转换为完整会话对象

#### `ConversationSnapshot`

职责：

- 表达完整会话快照
- 必须显式包含 `messages`
- 只在真正需要正文时构造

适用场景：

- 归档压缩
- rewind
- 导出
- 需要完整上下文的 LLM 输入准备
- 旧会话迁移

#### `MessageStore`

职责：

- 维护 `meta.json / manifest.json / messages.idx.json / blocks/*.jsonl`
- 只提供语义明确的原子能力

对上暴露：

- `read_meta`
- `read_recent_messages`
- `read_message_by_id`
- `read_messages_before`
- `read_messages_after`
- `append_messages`
- `replace_last_message`
- `truncate_after`
- `rebuild_from_snapshot`

不对上暴露：

- `cleanup_stale_*`
- 任意“按文件名删块”
- 半成品“全量重写但让上层自己决定何时调用”

约束：

- `rebuild_from_snapshot` 不属于普通业务能力
- 它只能被以下三类流程调用：
  - 全量导入
  - 全量导出同步回灌
  - 数据迁移恢复

## 五、推荐接口

### 1. 只读接口

```text
get_conversation_meta(conversation_id) -> ConversationMeta
get_conversation_snapshot(conversation_id) -> ConversationSnapshot
get_conversation_last_block(conversation_id) -> BlockPage
get_conversation_block(conversation_id, block_id) -> BlockPage
get_recent_messages(conversation_id, limit) -> Vec<ChatMessage>
get_messages_before(conversation_id, anchor_id, limit) -> MessagePage
get_messages_after(conversation_id, anchor_id, limit) -> MessagePage
list_conversations(filter, page) -> ConversationMetaPage
batch_get_conversation_meta(conversation_ids) -> Vec<ConversationMeta>
query_conversations(query) -> ConversationMetaPage
```

规则：

- 不需要正文的地方，只能调用 `get_conversation_meta`
- 需要正文时，必须显式调用 `get_conversation_snapshot` 或分页消息接口
- 块级读取必须显式走 block API，不能靠整会话再自行切块
- 会话列表与批量查询只能返回 `ConversationMeta`，不能顺手带全量消息

### 2. metadata 写接口

```text
update_conversation_title(conversation_id, title)
update_conversation_unread_count(conversation_id, unread_count)
update_conversation_todos(conversation_id, todos)
update_conversation_goal(conversation_id, goal)
update_conversation_routing(conversation_id, department_id, agent_id, kind)
create_conversation(input) -> ConversationMeta
delete_conversation(conversation_id)
```

规则：

- metadata 更新函数只允许修改 meta 字段
- 绝不能重算 message-derived 字段
- `message_count / preview_messages / latest_summary_title` 只能由消息存储层维护
- 创建会话只创建空会话元信息与空消息仓库，不允许复用伪快照对象
- 删除会话必须通过服务层统一清理 meta/index/runtime pointer/pending 状态

### 3. 正文写接口

```text
append_message(conversation_id, message)
append_messages(conversation_id, messages)
replace_last_assistant_message(conversation_id, message)
rewind_conversation_from_message(conversation_id, anchor_message_id)
revoke_message_and_following(conversation_id, message_id)
insert_summary_at_block_head(conversation_id, block_id, summary_message)
compact_block_for_archive(conversation_id, block_id, strategy) -> BlockCompactionResult
archive_conversation(conversation_id)
```

规则：

- 正文写入必须以磁盘真实状态为准
- 不允许由上层传入“疑似完整会话对象”要求底层自己猜
- `revoke_message_and_following` 是语义接口，不是“删除某条再让调用方自己删后面”
- `revoke_message_and_following` 的回撤范围不能跨多个块，最多只允许覆盖“锚点所在块”或“锚点所在块 + 紧邻上一个块”
- `insert_summary_at_block_head` 只能插在块头，不能对任意 offset 插入
- `compact_block_for_archive` 只允许做“工具内容瘦身、保留正文与思维链”的归档优化，不允许改变消息先后顺序
- 普通正文接口一律不允许覆写整会话

### 3.5 特批覆写接口

```text
import_conversation_snapshot(import_job_id, snapshot) -> ImportResult
sync_replace_conversation_snapshot(sync_job_id, snapshot) -> SyncReplaceResult
recover_conversation_snapshot(recovery_job_id, snapshot) -> RecoveryResult
```

规则：

- 这三类接口是唯一允许整会话覆写的口子
- 必须显式带 `job_id / source / operator / reason`
- 必须在审计日志中记录“导入 / 同步 / 迁移恢复”来源
- 不得被普通聊天、工具、调度、任务、远程 IM 路径复用

### 4. 流式接口

```text
begin_stream_turn(conversation_id, stream_context) -> StreamHandle
append_stream_delta(stream_handle, delta)
append_stream_reasoning_delta(stream_handle, delta)
append_stream_tool_event(stream_handle, event)
commit_stream_message(stream_handle) -> CommitResult
abort_stream_message(stream_handle) -> AbortResult
recover_incomplete_stream(conversation_id) -> RecoveryResult
```

规则：

- 流式阶段的数据先进入运行态缓存，不直接污染持久化快照
- 只有 `commit_stream_message` 才能把本轮流式结果固化进消息仓库
- `abort_stream_message` 必须保持“已提交工具结果”和“未提交正文”语义分离

### 4.1 已有 assistant 消息的增量追加接口

```text
append_tool_event_to_assistant_message(conversation_id, assistant_message_id, assistant_tool_event, tool_result_event, provider_meta_patch?) -> AppendToolEventResult
append_final_text_to_assistant_message(conversation_id, assistant_message_id, final_text, reasoning_text?, provider_meta_patch?) -> AppendFinalTextResult
```

规则：

- 这是一个特殊正文接口，只允许作用于“当前轮最后一个可写 assistant message”
- 目的不是覆写整条消息，而是对既有 assistant message 做增量追加
- `append_tool_event_to_assistant_message` 只允许给“尚未拥有 final 正文”的 assistant message 追加工具事件
- 一旦 assistant message 已经拥有 final 正文，后续禁止再追加任何 tool call / tool result
- `append_final_text_to_assistant_message` 允许只补 final 正文，也允许同时补 reasoning / provider_meta patch
- final 正文允许缺失；如果流式被压缩、中断、引导终止，消息可以停留在“只有 tool history / reasoning，没有 final 正文”的合法状态
- 工具事件追加必须保持组级原子性，不能只落 assistant tool call 不落 tool result
- final 正文追加成功后，该 assistant message 进入 `FinalizedForToolAppend=false / ToolAppendClosed=true` 终态
- 已归档 block、已撤回消息、非最后可写 assistant message 一律禁止走该接口
- 该接口必须走 message-id 定位与尾部一致性校验，不能退化成“整条消息读出、整体替换、再写回”

补充说明：

- `final_text` 为空不代表该次提交无效；只要该轮语义上已经结束，服务层仍可把该消息推进到 `ToolAppendClosed=true` 终态
- 这样可以覆盖“仅工具历史 / 仅 reasoning / 被压缩打断 / 引导中止”这些合法半轮结束场景

### 5. 工具调用原子接口

```text
begin_tool_group(conversation_id, assistant_message_id?, tool_group_meta) -> ToolGroupHandle
append_tool_call_event(tool_group_handle, assistant_tool_event)
append_tool_result_event(tool_group_handle, tool_result_event)
commit_tool_group(tool_group_handle) -> ToolGroupCommitResult
abort_tool_group(tool_group_handle) -> ToolGroupAbortResult
```

规则：

- 同一组工具调用必须以“组”为单位提交，不能把 assistant tool call 与 tool result 拆成跨事务写入
- `assistant_tool_event + tool_result_event + provider_meta_patch` 必须原子进入同一条 assistant message 或同一组追加语义
- 组内事件去重必须基于稳定 `tool_call_id`

## 六、禁止接口

以下能力不应再被业务层直接使用：

```text
ConversationShardMeta -> Conversation 的隐式桥接
to_metadata_conversation()
read_metadata_or_pending_conversation()
业务层直接调用 write_jsonl_snapshot_directory_shard()
业务层直接调用 cleanup_stale_conversation_block_files_by_names()
业务层直接调用 read_ready_message_store_* / write_jsonl_snapshot_* / read_conversation_meta_shard()
```

原因：

- 这些接口会把“不完整对象”和“完整对象”混淆
- 会把底层危险原语暴露给错误层级
- 会破坏“所有消息读写必须经由会话服务”的唯一边界

## 七、状态维护原则

### 1. 谁维护 message-derived 字段

以下字段只能由消息存储层在真实消息变更时维护：

- `message_count`
- `body_message_count`
- `body_text_length`
- `preview_messages`
- `has_assistant_reply`
- `has_context_compaction_message`
- `latest_summary_title`
- `last_message_at`

### 2. 谁维护纯 metadata 字段

以下字段可以由会话服务 metadata 更新接口维护：

- `title`
- `status`
- `summary`
- `unread_count`
- `current_todos`
- `preferred_api_config_id`
- `auto_push_remote_contact_id`
- `shell_workspace_path`
- `plan_mode_enabled`
- `active_goal`

## 八、并发模型与一致性

### 1. 单会话串行

同一会话的以下操作必须串行化：

- append / replace / rewind / revoke
- block 归档优化
- 摘要插入
- 流式 commit
- 会话删除

原因：

- 这些操作都改变消息仓库结构或派生字段
- 必须保证 `meta / manifest / index / blocks` 观察到的是同一版本

### 2. 多会话并发

不同会话可以并发执行，但必须满足：

- 每个会话有独立锁或独立 actor
- 不共享可变消息快照
- 跨会话批量查询只能读 meta 或只读分页消息

### 3. 一致性规则

每次提交后必须同时满足：

1. `meta.message_count == manifest.source_message_count == index.items.len()`
2. `meta.last_message_at` 与 index 最后一条消息一致
3. `preview_messages` 与真实消息尾部投影一致
4. `body_message_count / body_text_length` 与当前正文一致

### 4. 原子提交边界

推荐提交顺序：

```text
write blocks temp
-> write index temp
-> write manifest temp
-> write meta temp
-> atomic rename / replace
-> cleanup stale blocks
```

关键点：

- stale block cleanup 必须是提交成功后的尾动作
- cleanup 前必须已有可读的新 index / manifest / meta
- 如果提交中断，应优先保留旧可读版本而不是进入半空状态

### 5. 工具调用消息原子性

工具调用消息必须满足以下一致性：

1. assistant 发起工具组消息与对应 tool result 不能落在两个互不关联的持久化事务里
2. 如果创建了新的 assistant message，则该 message 的 tool history 必须整体可重放
3. 如果只是向最后一条 assistant message 追加工具结果，则必须保证：
   - 目标 message id 稳定
   - 组内 assistant tool call 不重复插入
   - tool result 不重复插入
4. 中途失败时，允许整组不提交；不允许提交半组后再靠补丁猜修

建议：

- 工具调用写入使用单独的 `ToolGroupCommit` 语义对象
- commit 前先在运行态组装完整结果，commit 时一次性落盘
- 对“最后一条 assistant message 被替换/追加”的路径做幂等保护

## 九、错误恢复与完整性策略

### 1. 启动期恢复

启动或首次读取会话时，服务层应做轻量完整性检查：

- `meta.json` 是否可读
- `manifest.json` 是否可读
- `messages.idx.json` 是否可读
- index 引用的 block 是否全部存在
- block 内消息 JSONL 是否可逐条解析
- index 中 message_id 是否唯一且严格按会话顺序排列
- block 边界是否与 index 的 block_id 顺序一致

### 2. 恢复策略分级

#### 级别 A：可自动修复

- manifest 计数滞后但 index/block 完整
- meta 派生字段与 index 不一致
- preview / latest_summary_title 与真实尾消息不一致

处理：

- 直接从 index/block 重建 manifest 或 meta 派生字段

#### 级别 B：需要局部降级

- 个别 block 缓存损坏
- 最近块缺失但旧块完整
- index 可读但部分 offset/byteLen 指向无效内容

处理：

- 禁止写入
- 退回只读或局部恢复模式
- 记录恢复日志

#### 级别 C：结构性损坏

- index 为空但 blocks 非空
- meta/manifest/index 三者版本断裂
- cleanup 后只剩尾块且计数不一致
- block_id 顺序回退或跳号且无法与 index 对齐
- tool message 事务只写入了一半，无法重放为完整 assistant 历史

处理：

- 阻止继续 append
- 进入恢复流程
- 优先从 block 实际内容重建 index 和派生字段
- 无法修复时转备份并显式报错

### 3. 完整性守卫

服务层应显式禁止以下危险提交：

- `message_count == 0` 但磁盘已有 block
- 输入 snapshot 的 `messages` 为空，但 ready store 显示已有历史
- 试图基于 metadata-only 对象触发 full rewrite

### 4. 存储完整性校验清单

建议把完整性校验拆成显式能力：

```text
validate_meta(conversation_id)
validate_manifest(conversation_id)
validate_index(conversation_id)
validate_blocks(conversation_id)
validate_cross_file_consistency(conversation_id)
repair_from_blocks(conversation_id)
rebuild_meta_from_store(conversation_id)
rebuild_manifest_from_store(conversation_id)
```

交叉校验至少包含：

1. `meta.message_count == manifest.source_message_count == index.items.len()`
2. index 中每个 `(block_id, offset, byte_len)` 都能读出合法消息
3. index 尾消息 id 与 manifest / meta 尾标记一致
4. preview、summary title、assistant reply 标记与真实消息尾部投影一致
5. assistant tool history 不存在“缺 assistant tool call 只有 result”或“缺 result 只有 call”的破组状态

### 5. 恢复策略原则

- 优先相信真实 block 内容，而不是 meta/manifest 的派生计数
- 能从 block 重建的，就不要从 cache 或运行态推断
- 恢复动作必须显式记日志，并带会话 id、损坏级别、恢复来源
- 自动恢复后必须重新跑一次完整性校验，确认恢复结果可读

## 十、流式消息语义

### 1. 流式消息生命周期

```text
begin_stream_turn
-> delta / reasoning / tool events
-> assemble transient message
-> commit_stream_message
-> append to store
```

### 2. 流式期间允许的状态

- 正文可能为空，但 reasoning 已有内容
- 工具调用历史可能已完成，但最终 assistant 正文还未提交
- 中断时必须区分“可落盘的已完成部分”和“仅运行态缓存”
- 对既有 assistant message 的增量追加只能沿一个方向推进：
  - 可以先追加 tool history，后追加 final 正文
  - 不允许先落 final 正文，再回头追加 tool history

### 3. 流式提交规则

- reasoning-only 完成消息允许落盘
- 工具结果已提交时，不能因正文为空而丢弃整轮结果
- stream commit 必须生成稳定 message id，不允许事后替换导致索引漂移
- 如果采用“已有 assistant message 增量追加”模式：
  - `append_tool_event_to_assistant_message` 与 `append_final_text_to_assistant_message` 必须共享同一 message id
  - 追加 tool 之前必须验证目标消息还没有 final 正文
  - 追加 final 正文之后必须关闭后续 tool append 能力

### 3.1 assistant 消息增量追加状态机

```text
OpenForToolAppend
  -> ToolHistoryGrowing
  -> FinalTextCommitted

ToolHistoryGrowing
  -> ToolHistoryGrowing
  -> FinalTextCommitted
  -> AbortedWithoutFinalText

FinalTextCommitted
  -> Closed

AbortedWithoutFinalText
  -> Closed
```

规则：

- `FinalTextCommitted` 之后禁止再进入 `ToolHistoryGrowing`
- `AbortedWithoutFinalText` 是合法终态，不视为损坏
- `Closed` 表示该消息已不再接受任何结构性追加，只允许读取或被后续归档优化读取

### 4. 流式恢复

如果程序崩溃在流式中途：

- 未 commit 的 delta 只允许丢失运行态缓存
- 已 commit 的工具结果和 assistant message 必须可重放
- 恢复逻辑必须能识别“半轮结束”并安全回到 idle

### 4.1 `meme_annotations` 与错误的 `inlineSegments`

`meme_annotations` 是当前应保留的正式 meme 语义；`inlineSegments` 与 `provider_meta.memeSegments` 都不是正式消息真相源，不应继续作为前端渲染依赖或消息持久化依据。

规则：

- `meme_annotations` 表达“把正文中的某个 meme token 替换成 markdown 图片引用”的明确替换语义
- 前端应直接基于消息正文 markdown 渲染；如需处理 meme，占位替换应基于 `meme_annotations` 完成
- 后端禁止继续把正文语义派生为 `providerMeta.inlineSegments` 供前端渲染
- 后端也禁止把 `provider_meta.memeSegments` 当作正式持久化真相；若历史兼容或远程发送适配仍暂时需要结构化拆段，也必须从正文 + `meme_annotations` 派生，而不是反过来主导消息语义
- `inlineSegments` 若仍存在，只能视为待清理的错误遗留，不得继续扩散到新链路
- `provider_meta.memeSegments` 若仍出现在历史计划或历史数据讨论中，只能视为阶段性旧方案名词，不代表当前实现边界
- 归档、压缩、恢复、导入导出时，正文语义应以消息正文与 `meme_annotations` 为准，而不是 `inlineSegments` 或 `provider_meta.memeSegments`

## 十一、消息分页锚点语义

### 1. 分页模型

消息读取应默认以锚点分页，而不是整读：

```text
get_recent_messages(conversation_id, limit)
get_messages_before(conversation_id, anchor_message_id, limit)
get_messages_after(conversation_id, anchor_message_id, limit)
get_block_page(conversation_id, block_id)
```

### 2. 锚点定义

- `anchor_message_id` 表示一条已存在的稳定消息 id
- `before(anchor)` 返回严格位于锚点之前的消息
- `after(anchor)` 返回严格位于锚点之后的消息
- 锚点本身默认不包含在结果中，除非显式定义 `inclusive`

### 3. 语义要求

1. 锚点必须基于全局消息顺序，不允许只在单个 block 内局部解释
2. 当锚点所在 block 被缓存、瘦身、归档优化后，锚点语义仍必须稳定
3. 工具调用消息、摘要消息、压缩上下文消息也必须拥有可分页的稳定 message id
4. 分页结果必须返回：
   - `messages`
   - `has_more_before`
   - `has_more_after`
   - `first_message_id`
   - `last_message_id`

兼容要求：

- 如果为了兼容旧调用方暂时保留 `has_more`，它只能作为 `has_more_before || has_more_after` 的兼容投影
- 新调用方禁止再依赖单个 `has_more` 猜测“到底前面还有还是后面还有”

### 4. 块与锚点的关系

- block 是物理分页单位
- anchor 是逻辑分页单位
- 逻辑 API 不能把“某条消息恰好跨 block”这类物理细节泄漏给上层

也就是说：

- 上层按 message id 翻页
- 存储层内部决定要读哪个 block、是否跨 block 拼接

### 5. 特殊消息的锚点规则

- `insert_summary_at_block_head` 插入的摘要消息必须拥有稳定 id，并成为该 block 内最早可见锚点
- `revoke_message_and_following` 后，所有被删消息的锚点必须失效，并返回明确的“anchor not found / anchor revoked”错误
- `revoke_message_and_following` 不能跨多个块级联删除，最大回撤窗口仅覆盖用户当前可合理感知的近邻块范围
- 被归档优化的工具消息如果保留 message id，则锚点继续有效；如果消息被语义合并，则必须建立旧 id 到新摘要消息的映射或显式报失效

### 6. 撤销范围限制

撤销消息能力必须显式受限：

1. 默认只允许撤销“锚点消息之后”的尾部范围
2. 最大只允许影响：
   - 锚点所在块
   - 或锚点所在块与其紧邻上一个块
3. 禁止跨两个以上历史块做大范围尾删

原因：

- 用户在界面上通常只能感知最近一到两个块范围
- 超出该范围的撤销很容易造成误删，且难以及时被用户发现
- 限制回撤窗口可以显著降低错误恢复成本

建议接口语义：

```text
revoke_message_and_following(conversation_id, message_id, scope=local_blocks)
```

其中：

- `local_blocks` 是默认且唯一允许的业务语义
- 如果锚点距离当前尾部超过允许窗口，应直接返回错误而不是执行跨多块删除

## 十一点五、唯一入口约束

项目内关于会话消息的所有正常业务访问，必须遵守唯一入口原则：

### 允许

- `conversation_service` 的只读接口
- `conversation_service` 的正文写接口
- `conversation_service` 的 metadata 写接口
- 显式恢复/修复模块内部，经批准调用 facade/internal 修复能力
- 导入/导出同步/迁移模块调用特批覆写接口

### 禁止

- UI、调度器、任务系统、远程 IM、工具运行时直接调用 message store 底层函数
- 业务模块自己组合 `meta + messages`
- 业务模块自己决定 full rewrite / cleanup / truncate 的实现细节
- 业务模块直接读取某个 block 文件后自行解释为正式会话状态
- 普通业务路径借用导入/同步接口做“图省事的整会话覆盖”

### 审查标准

只要出现以下任一情况，就应视为违规：

1. 非恢复代码直接 import/调用 message store 底层读写函数
2. 非服务层代码直接读取 `meta.json / manifest.json / messages.idx.json / blocks/*.jsonl`
3. 调用方自行拼装完整会话快照并要求底层写入
4. 调用方绕过服务层直接做分页、截断、替换、清理 block
5. 非导入/同步/迁移模块调用整会话覆写能力

## 十二、状态机

### 1. 会话运行状态机

```text
Idle
  -> Streaming
  -> ToolCommitting
  -> Rewinding
  -> Archiving
  -> Deleting

Streaming
  -> Idle
  -> ToolCommitting
  -> Aborted
  -> Failed

ToolCommitting
  -> Idle
  -> Failed

Rewinding
  -> Idle
  -> Failed

Archiving
  -> Idle
  -> Failed

Deleting
  -> Deleted
  -> Failed
```

规则：

- 同一时刻一个会话只能处于一个写态
- `Idle` 是唯一允许进入新写事务的入口
- `Streaming -> ToolCommitting` 允许，但必须属于同一轮 assistant turn
- `Deleted` 为终态，后续只允许恢复或报不存在

### 2. 消息存储状态机

```text
Ready
  -> Building
  -> Validating
  -> Repairing

Building
  -> Ready
  -> Corrupted

Validating
  -> Ready
  -> Degraded
  -> Corrupted

Repairing
  -> Ready
  -> Degraded
  -> Corrupted

Degraded
  -> Repairing
  -> ReadOnly

ReadOnly
  -> Repairing
  -> Corrupted

Corrupted
  -> Repairing
  -> BackupOnly
```

规则：

- `Ready` 之外的状态默认禁止普通写入
- `Degraded` 允许局部读取，不允许追加正文
- `ReadOnly` 明确表示只能读，不能进入任何写事务
- `BackupOnly` 表示已无法保证在线恢复，必须转人工处理

### 3. 工具组状态机

```text
Pending
  -> Collecting
  -> Aborted

Collecting
  -> ReadyToCommit
  -> Aborted
  -> Failed

ReadyToCommit
  -> Committed
  -> Failed

Committed
  -> Replayed
```

规则：

- `assistant_tool_call` 与 `tool_result` 收齐前不能进入 `Committed`
- 任何组内事件缺失都不能伪造成功态

## 十四、事务边界表

| 操作 | 读取范围 | 写入范围 | 是否原子 | 失败后要求 |
|---|---|---|---|---|
| `update_conversation_title` | meta | meta | 是 | 不影响消息仓库 |
| `append_message` | meta + tail/index | block + index + manifest + meta | 是 | 不允许只写入部分文件 |
| `append_messages` | meta + tail/index | block + index + manifest + meta | 是 | 不允许只写入部分文件 |
| `replace_last_assistant_message` | tail block + meta | block + index + manifest + meta | 是 | 原 message 与新 message 二选一可读 |
| `revoke_message_and_following` | anchor 前后 + index + block | block + index + manifest + meta | 是 | 撤回范围要么全删，要么完全不删 |
| `insert_summary_at_block_head` | target block + meta | target block + index + manifest + meta | 是 | 禁止只插 block 不改 index |
| `compact_block_for_archive` | target block | target block + manifest + meta | 是 | 失败时保留原 block |
| `commit_tool_group` | tail message / tool group cache | block + index + manifest + meta | 是 | 不允许半组提交 |
| `commit_stream_message` | stream cache + meta | block + index + manifest + meta | 是 | 未 commit delta 不入仓 |
| `archive_conversation` | snapshot/meta | block/index/meta/manifest + archive state | 是 | 失败时原会话仍可读 |
| `delete_conversation` | meta + runtime refs | conversation dir + index refs + runtime refs | 是 | 不允许删目录但残留主指针 |
| `repair_from_blocks` | all blocks + index/meta/manifest | index + manifest + meta | 是 | 修复后必须重验 |

### 事务原则

1. metadata-only 事务不能触碰 block/index/manifest
2. message-changing 事务必须同时提交 `block + index + manifest + meta`
3. cleanup 不是事务主体，只能是提交成功后的尾动作
4. 所有事务都必须能回答“失败后当前磁盘仍然是哪一个完整版本”

## 十五、一次性重构目标

### 第一阶段

- 保留 `Conversation` 作为完整快照模型
- 新增 `ConversationMeta` 视图模型
- 所有 metadata-only 链路改吃 `ConversationMeta`
- 停止新增任何 `meta -> Conversation(messages=[])` 的桥接

### 第二阶段

- 收口 `conversation_service` 的公开方法
- message store 全量重写能力下沉到 facade/internal
- 业务层不再接触危险重写原语

### 第三阶段

- 删除历史桥接接口
- 删除依赖伪完整会话的旧 helper
- 为 metadata-only / snapshot-only 各自建立独立测试集

## 十六、验收标准

满足以下条件，说明服务边界已经正确：

1. 仓库中不存在 `ConversationShardMeta -> Conversation(messages=[])` 的桥接 API。
2. metadata-only 更新不会改变任何 message-derived 字段。
3. append 路径不再依赖上层传入的“完整会话对象”判断是否全量重写。
4. 业务层无法直接调用删块逻辑。
5. 所有“只看状态/类型/标题”的逻辑都能直接吃 meta，不必先转 `Conversation`。
6. 已存在 block 的会话不会因为 message_count 判断错误进入 seed/full rewrite。
7. 块级读取、块归档优化、消息撤回、摘要插入都走显式语义接口。
8. 流式 commit、中断、恢复三条链路都可独立验证。
9. 会话删除、批量查询、并发追加具备一致性约束与恢复策略。
10. 工具调用消息满足组级原子提交与幂等保护。
11. 分页 API 的锚点语义稳定，不因 block 优化或摘要插入失真。
12. 存储损坏时具备分级校验、恢复与降级策略。
13. 会话/存储/工具组三套状态机可映射到实现代码。
14. 所有对外失败路径都有稳定错误码。
15. 每个写操作都能落到明确事务边界表中的一种。

## 十七、结论

`conversation_service` 的价值，不是提供“所有底层能力”，而是提供“业务允许的能力”。

因此，正确的会话服务必须：

- 隐藏底层危险原语
- 区分 metadata 与 full snapshot
- 禁止伪完整对象流入写盘链路

只有这样，服务层才真正有存在意义。
