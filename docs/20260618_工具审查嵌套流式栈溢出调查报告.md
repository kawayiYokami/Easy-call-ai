# 20260618 工具审查嵌套流式栈溢出调查报告

## 一、问题概述

2026-06-18 在终端工具 `exec` 的智能审查链路中，持续出现：

- `thread 'tokio-rt-worker' (...) has overflowed its stack`

当前问题的核心现象不是“普通模型请求失败”，而是：

- 主聊天 / 工具循环外层已经处于流式请求中
- 工具执行阶段又立刻触发一条新的“快速请求 / 智能审查流式请求”
- 第二条流建立成功后，在首次消费流事件前后直接导致 Tokio worker 栈溢出

这意味着：

- 崩溃发生在 Tauri 后端 Tokio worker
- 崩溃不是可恢复的 `Result::Err`
- 崩溃会直接导致主进程退出

---

## 二、本次调查结论

### 1. 当前问题不应再按“业务递归”描述

本轮新增日志已经证明：

- 聊天流式重绑回调的重入深度始终为 `depth=1`
- 未观察到流式事件分发自身递归增深
- 未观察到 `assistant_tool_result -> stream_rebind_required -> assistant_tool_result` 这类明显闭环

因此，当前问题不应再使用“上层递归导致爆栈”作为主口径。

更准确的描述是：

**同一 Tokio worker 线程内，外层流式请求尚未完全退出其底层消费上下文时，又立刻发起并消费另一条新的流式请求，触发了底层流式依赖栈溢出。**

### 2. 崩溃点已经定位到“第二条流开始消费”阶段

本轮日志链路已确认：

1. `exec` 命令进入智能审查
2. 智能审查上下文构建完成
3. `run_tool_smart_review()` 开始调用模型
4. `call_model_openai_stream_internal()` 完成：
   - 鉴权配置
   - provider gate
   - adapter 选择
   - request 构建
   - client 构建
   - `exec_chat_stream(...)`
5. 日志已经打印：
   - `[推理请求] 流已建立 openai_stream ...`
6. 随后立刻发生：
   - `thread 'tokio-rt-worker' (...) has overflowed its stack`

因此可以明确：

- 不是请求体构建阶段
- 不是 provider gate 等待阶段
- 不是 client 构建阶段
- 不是 `exec_chat_stream(...).await` 建流阶段

而是：

**流已建立后，第一次消费流事件的最早阶段。**

### 3. 冲突对象更像“主聊天流 vs 工具审查流”

当前日志未显示多个工具审查流同时并行：

- 工具审查模型配置当前 provider gate 为 `max=1`
- 没有观察到“审查流 A 未结束，审查流 B 又进入”的证据

但已经可以确认：

- 外层聊天 / tool loop 仍处于 `mode=stream`
- 工具执行期间又触发了新的 `openai_stream`

因此当前最可信的冲突关系不是：

- 审查流 A vs 审查流 B

而是：

- **外层主聊天流 vs 内层工具审查流**

### 4. 这次崩溃发生在外层 tool loop 第 3 轮之后

本次日志中已出现：

- `[聊天] 工具循环轮次开始 ... mode=stream round=3`
- 第 3 轮模型返回 `tool_calls=2`
- 随后开始执行 `exec`
- `exec` 的智能审查流建立成功后爆栈

因此，本次样本可以明确归类为：

- 外层 `tool loop` 第 3 轮工具执行阶段
- 当前这次 `exec` 的智能审查流式请求直接触发崩溃

## 三、已排除项

本轮调查已明确排除以下方向：

### 1. 不是流式重绑递归

重入日志始终为 `depth=1`，未观察到深度不断增长。

### 2. 不是 shell 命令真实执行阶段

多次样本都显示：

- `builtin_shell_exec()` 的命令分析、审查前准备、实际命令执行都可正常完成
- 对于不触发智能审查的只读命令，命令本身可稳定成功

### 3. 不是会话落盘或 tool result 回写阶段

新增日志已确认以下步骤可正常完成：

- `append_tool_group_result`
- `persist_replaced_ready_message`
- metadata / ready message 替换

### 4. 不是“整会话 JSON 导出 / clone”这个旧问题的直接重现

虽然当前热路径里仍有若干整消息列表 clone，但本轮崩溃日志已经说明：

- 崩溃点落在“流建立后立即消费”阶段
- 并不落在会话快照导出或持久化写回阶段

因此，当前问题与历史上“超大对象物化/clone 导致栈溢出”的口径不同，不能混为一谈。

## 四、当前最可信的技术判断

结合日志与历史经验，当前最可信的判断如下：

### 1. 根因更接近底层流式依赖，而不是业务层

当前表现非常像：

- 最底层 request / stream / SSE 消费依赖
- 在同一线程内处理“流中再起流”时存在不安全行为

换句话说：

- 问题不一定在 `genai` 业务封装层
- 更可能位于 `genai` 之下的 request / stream 消费链

### 2. “非流式兜底”不能作为默认修法

当前模型配置并不保证所有 provider / model 都支持非流式。

因此：

- “工具审查统一改 non-stream” 不是可接受的长期方案
- 对快速请求的设计应默认按“流式可用、非流式不保证可用”来约束

### 3. 快速请求不应继续复用当前重推理网关

目前工具审查 / 快速请求复用了统一推理网关，继承了以下副作用：

- provider gate
- 流式 / 非流式策略
- fallback
- 模型调用日志
- usage 处理

这条路径过重，而且在“外层已有流”的情况下会再次进入流式请求链。

后续应将“快速请求”视为独立能力，而不是“普通推理场景的一个 scene”。

---

## 五、对“快速请求”的新约束建议

基于本次调查，建议后续把“快速请求”定义为独立通道，并采用以下约束：

1. 快速请求默认视为独立能力，不再复用当前重推理网关。
2. 快速请求任何情况下都不写模型调用日志。
3. 快速请求任何情况下都不写 usage。
4. 快速请求需要重点规避“同线程内嵌套流式消费”。

当前还未最终确认“规避方式”的具体实现，但已明确：

- 不能再把“快速请求只是一个普通 scene”继续放在现有统一链路里。

## 六、后续实现方向备忘

本轮调查只形成结论，不在本文内直接定稿实现方案。当前讨论过的方向包括：

### 方向 A：快速请求独立线程 / 独立 runtime

目标：

- 避免与外层主聊天流共享同一个 Tokio worker 线程

注意：

- `tokio::spawn` 不能保证切换到新线程
- 若采用该方案，必须是独立 OS 线程，且在线程内部重建 runtime 与模型请求对象

### 方向 B：外层流式进行中时，不允许再次进入“模型型工具审查”

目标：

- 从业务上规避“流中再起流”

可选降级方式：

- 本地规则 + 用户确认
- 或延后到外层流结束后再做

### 方向 C：继续深挖底层依赖版本与历史问题

目标：

- 结合 `Cargo.lock` 与历史排查记录，确认是否命中过去已知的 request / stream 依赖问题

## 八、当前结论摘要

截至 2026-06-18，本问题的调查结论可以总结为：

1. 当前爆栈不是上层业务递归。
2. 当前爆栈不是 shell 命令执行本体、不是会话写回、也不是旧的整会话 clone 问题。
3. 当前爆栈发生在：**外层主聊天流仍在进行时，工具审查又在同线程发起并开始消费第二条流。**
4. 第二条流已经成功建立，崩溃发生在其首次消费阶段。
5. 当前最可信的根因位于更底层的 request / stream 消费依赖，而不是业务层状态机本身。
6. “快速请求”后续必须从当前重推理网关语义里拆出来单独设计。
