# 工具执行结果占位符下发计划

## 背景

- 当前前端最容易崩的热点之一，不是普通消息正文，而是 assistant 消息里夹带的大体积工具执行结果。
- 这些结果常见于：
  - shell / exec 大段 stdout
  - browser snapshot / 页面抓取原文
  - 大 JSON 查询结果
  - 大文件读取正文
- 对聊天主界面来说，这些原文默认展示价值很低，但会显著放大 IPC、反序列化、响应式追踪、消息投影和列表渲染成本。

## 计划目标

本计划只解决一件事：

1. **工具执行结果默认不向前端下发原文，只下发占位信息**
   - 前端仍能知道“调用过什么工具、是否完成、参数大意是什么”
   - 前端默认不承载大体积工具结果正文
   - 原始磁盘存储先保持不变

## 非目标

- 本计划不修改 message store 文件格式。
- 本计划不删除历史会话中的原始工具结果。
- 本计划不重做工具时间线 UI。
- 本计划不在本阶段提供“查看完整工具原文”的新入口。
- 本计划不处理普通 assistant 文本正文的裁剪。

## 需求

### 需求 A：工具结果默认替换为占位符

- **A-R1 默认不下发原始结果正文**：stdout、snapshot、网页原文、长 JSON、文件正文等高体积结果不得默认传给前端。
- **A-R2 保留工具骨架信息**：前端仍需拿到工具名、调用 ID、状态、参数摘要、事件顺序。
- **A-R3 提供明确占位标记**：前端收到的数据必须能明确识别“结果已省略”，不能伪装成完整结果。
- **A-R4 占位文案稳定**：同类结果使用统一占位文案，避免前端再根据原始内容做额外推断。

### 需求 B：占位结构必须足够支撑现有展示

- **B-R1 保留状态**：至少保留 `doing` / `done` 或等价状态，不能影响工具时间线的进行中与完成态。
- **B-R2 保留参数摘要**：允许保留短参数摘要，但不保留超长 arguments 原文。
- **B-R3 允许保留短结果摘要**：若某些工具结果天然很短，可保留短摘要；超过阈值时统一替换为占位符。
- **B-R4 保留裁剪标志**：建议包含 `resultOmitted`、`resultPreview`、可选 `resultSize` / `resultKind` 等字段，便于前后端协同。

### 需求 C：流式与最终消息必须同步口径

- **C-R1 覆盖流式工具事件**：流式期间送到前端的工具结果不得携带大原文。
- **C-R2 覆盖最终 assistantMessage**：轮次完成后回填的 assistant 消息也必须沿用同样的占位规则。
- **C-R3 覆盖 history_flushed**：历史刷入事件里的消息不得重新夹带完整工具结果。
- **C-R4 禁止“前轻后重”回流**：不能出现流式阶段是占位符、最终落库回读时又把完整结果塞回前端的情况。

## 实施范围

- 后端消息读侧投影
- 后端流式事件下发结构
- 前端工具时间线现有兼容验证

## 验收口径

- 包含超大工具结果的会话在聊天窗口打开、切换、分页、恢复时明显更稳定。
- 工具时间线仍能看到：
  - 调用了哪个工具
  - 当前是否完成
  - 参数大意
- 前端默认不再收到大段 stdout、snapshot、网页原文、长 JSON。
- 同一条消息在流式阶段、history_flushed、最终消息回填阶段，工具结果裁剪口径一致。

## 风险与边界

- 若现有前端某些显示细节仍隐式依赖完整工具结果，落地后可能暴露局部显示回归，需要补齐最小必要摘要字段。
- 这一步只能先解决“工具结果过重”这类主要爆点，不能替代后续对完整消息读侧、流式缓存和消息签名计算的继续瘦身。
- 若后续确实需要调试原文，应该新增按需详情接口，而不是回退到默认全量下发。
