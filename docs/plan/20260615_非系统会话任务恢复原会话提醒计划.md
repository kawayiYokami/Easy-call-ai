# 非系统会话任务恢复原会话提醒计划

状态：调查完成，待用户确认后实现

## 背景

用户反馈：此前有一轮改动把“非系统通知会话的任务”也收口到了系统侧后台委托语义，实际使用体验不符合预期。当前需要重新钉死边界，避免后续需求反复时再次漂移。

本计划只处理“任务触发后的投递边界”，不顺手扩散到任务 UI、委托展示、通知样式或模型策略。

## 已确认需求

本轮唯一有效口径：

- 只有显式绑定 `system-notification-conversation` 的任务，才是系统任务。
- 只要任务绑定的是非系统通知会话，就必须在原会话内由系统消息提醒，并在该原会话继续触发调度。
- 非系统通知会话任务不得再改走系统后台委托。
- 普通会话任务的执行结果应继续留在原会话，不写回 `P-ai系统`。
- 新建任务不存在空 `conversation_id`；在哪个会话创建，就绑定哪个会话。
- 空 `conversation_id`` 只视为异常遗留数据，当前仍继续按系统任务兼容。

可以把这条规则记成一句话：

> 系统任务走 `P-ai系统` 后台委托；非系统会话任务走原会话系统提醒 + 原会话调度。

## 调查结论

最相关的行为变更集中在 `2026-06-09` 的 `279c3847 fix(task): 收口系统任务与一次性调度语义`。

本次调查确认了 3 个关键收口点：

1. `src-tauri/src/features/task/store.rs`
   - 读库时把空 `conversation_id` 归一化成 `system-notification-conversation`
   - 创建和更新任务时也默认写成系统会话 ID

2. `src-tauri/src/features/task/scheduler.rs`
   - 调度解析时，空/缺失 `conversation_id` 会被直接视为系统任务
   - 系统任务不再在会话里投递提醒，而是直接创建独立后台委托

3. `src-tauri/src/features/chat/conversation_service/delegate.rs`
   - 委托结果写回边界被收紧，不再允许普通会话结果回退到系统通知会话

其中真正造成语义漂移的核心是第 1、2 点：任务读取和调度阶段把“未显式声明系统任务”的情况过早等同成了系统任务。

## 写死边界

### 1. 系统任务判定

仅以下情况属于系统任务：

- `task.conversation_id == system-notification-conversation`

除此之外一律不算系统任务。

### 2. 普通会话任务判定

以下情况属于普通会话任务：

- `task.conversation_id` 指向有效普通会话

普通会话任务的触发行为必须固定为：

- 到点时如果目标会话空闲，立即在原会话插入系统提醒消息
- 插入后立即通过原会话继续触发调度
- 执行结果留在原会话
- 到点时如果目标会话忙碌，本次跳过，不改走系统后台委托
- 当前这轮调度结束时，检查“本会话是否已有激活时间已过的任务”
- 若存在，则在原会话补发系统提醒并激活调度

### 3. 旧数据兼容

历史上 `conversation_id` 为空的任务，继续按系统任务兼容，这条不改。

兼容口径写死如下：

- 读库阶段允许把空 `conversation_id` 归一化成 `system-notification-conversation`
- 新建/编辑时，只要最终 `conversation_id` 为空，也仍按系统任务处理
- 这次修复不改“空 ID -> 系统任务”的兼容策略，只改“非系统通知会话任务”的分发路径

### 4. 缺失绑定会话

普通会话任务如果绑定了非系统会话 ID，但该会话已不存在：

- 任务失败结束
- 记录明确失败原因
- 不回退到 `P-ai系统`
- 不偷偷改成后台委托

### 5. 非目标

以下内容不在本轮范围内：

- 不修改系统任务仍走后台委托的策略
- 不修改任务“一次性任务触发即完成”的现有口径
- 不新建独立的全局 pending 任务队列
- 不调整任务侧栏样式、分组顺序、文案外观
- 不重做委托面板或通知系统
- 不补版本号、不做发布相关变更

## 计划修改范围

### 后端核心

  - 保留“空 `conversation_id` -> 系统任务”的兼容逻辑
  - 避免把非系统通知会话任务误并入系统任务分发路径

- `src-tauri/src/features/task/domain.rs`
  - 增加“原始绑定会话 ID”和“显式系统任务”判断辅助函数

- `src-tauri/src/features/task/scheduler.rs`
  - 重写任务分发判定：
    - 显式系统任务 -> 系统后台委托
    - 普通会话任务 -> 空闲时立即在原会话提醒并调度
    - 普通会话忙碌 -> 本次跳过，等待本会话本轮调度结束时补检查
    - 历史空会话任务 -> 继续按系统任务兼容

- `src-tauri/src/features/system/commands/chat_and_runtime/*`
  - 在现有会话调度收尾位置追加“本会话逾期任务补检查”
  - 仅检查当前会话，不做全局扫描
  - 命中后补发原会话系统提醒并激活调度

## 验收标准

用户确认前，以下都算未完成；只有全部满足才算本轮收口成功：

1. 从普通聊天会话创建的任务到点后：
   - 若会话空闲，会立即在原会话出现系统提醒
   - 后续回答继续发生在原会话
   - 不会跑去 `P-ai系统` 开后台委托

2. 从普通聊天会话创建的任务到点时若会话忙碌：
   - 本次不会插入系统提醒
   - 当前会话这轮调度结束后，会检查本会话是否存在已过激活时间的任务
   - 若存在，会在原会话补发系统提醒并激活
   - 仍不会转成系统后台委托

3. 从 `P-ai系统` 创建的任务到点后：
   - 仍走系统任务后台委托
   - 结果仍归到 `P-ai系统`

4. 普通会话任务绑定会话丢失时：
   - 任务失败
   - 不回退到系统会话
   - 不转后台委托

5. 历史空 `conversation_id` 任务：
   - 继续按系统任务兼容
   - 行为与显式系统任务保持一致

## 实施顺序

1. 保留任务读取时“空 ID -> 系统任务”的兼容逻辑
2. 改任务到点分发分支：
   - 普通会话空闲则立即插入并激活
   - 普通会话忙碌则跳过
3. 在现有会话调度结束收尾处补一轮“本会话逾期任务检查”
4. 最后补最小必要测试，锁住这次边界
