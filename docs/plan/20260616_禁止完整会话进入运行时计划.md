# 20260616_禁止完整会话进入运行时计划

## 1. 结论

这次不是“优化会话缓存”，也不是“减少一点内存占用”。

真正要修的是一条被实现破坏掉的硬边界：

- **完整会话不允许进入运行时**
- **完整会话不允许进入内存缓存**
- **完整会话不允许成为任何服务层/调度层/前台列表层的通用对象**

如果某条链路需要先拿一个 `Conversation` 再从里面摘自己要的字段，这条链路本身就是设计错误。

## 2. 本次要钉死的需求边界

### 2.1 运行时允许存在的数据形态

运行时只允许存在以下几类数据：

- `chat_index`
- 轻量 `conversation metadata`
- 当前会话的最近消息页
- 当前会话的最近块
- 指定锚点前后的有限消息窗口
- 单条消息
- 调度中的流式尾部状态
- 前台会话的运行时投影

### 2.2 运行时禁止存在的数据形态

运行时明确禁止：

- 完整 `Conversation`
- `HashMap<String, Conversation>`
- “metadata 名义下实际存整份 Conversation”
- 为列表/overview 预热全量消息正文
- 为调度方便预读整个会话
- 为切会话方便缓存整仓会话

这条禁止规则不是“默认不这么做”，而是**任何情况下都不允许**。

## 3. 消费方边界

### 3.1 overview / 会话列表

overview、前台会话列表、归档列表、联系人列表，只允许消费：

- `chat_index`
- `conversation metadata`
- 最近一条摘要来源消息或最近消息页

不允许：

- 读取完整会话
- 为了生成摘要遍历整段历史
- 为了展示列表把会话正文灌入缓存

正确语义：

- 首次列表：只读 `chat_index + metadata`
- 缺摘要时：按需补读最近消息页或最后一条相关消息
- 后续刷新：完全依赖调度结束时增量更新 metadata / recent page

### 3.2 调度

调度只允许消费：

- 当前会话 metadata
- 当前会话最近块
- 当前会话最近消息窗口
- 当前会话 runtime state

不允许：

- 读取其他会话正文
- 读取当前会话完整历史
- 把完整会话作为调度主对象

调度本质上只关心“当前会话尾部”，不关心“整个会话”。

### 3.3 前台切会话

前台切会话只允许消费：

- 会话 metadata
- 最近消息页
- 必要时按“向前翻页”补读更早消息
- 当前 runtime 投影

不允许：

- 切换时读取完整会话
- 为了“切起来快”提前常驻整会话

### 3.4 归档 / 搜索 / 其他后台能力

即使是归档、搜索、导出、任务、远程 IM，也不构成“完整会话可以存在于运行时”的豁免理由。

如果某个场景确实需要跨多条消息工作，也必须表达成：

- 有界消息窗口
- 分页扫描
- 块级扫描
- 按索引定位的小范围读取

而不是恢复成“先拿完整 `Conversation` 再处理”。

## 4. 当前实现的错误点

### 4.1 `cached_conversations` 是错误抽象

`cached_conversations: HashMap<String, Conversation>` 违反本计划的核心边界，必须移除。

它的问题不是“太大”，而是：

- 它让运行时默认接受“完整会话可驻留内存”
- 它诱导上层继续把 `Conversation` 当通用对象传递
- 它会让 overview / 调度 / 搜索路径自然滑向错误实现

### 4.2 `cached_conversation_metadata` 当前也是错误抽象

如果 `cached_conversation_metadata` 里存的是 `Conversation`，那它不是 metadata，它只是另一份整会话缓存。

这类实现必须改成真正的轻量结构。

### 4.3 `state_read_conversation_cached(...)` 是错误入口

只要这个入口的语义还是“读完整会话并放入缓存”，它就会持续污染所有上层。

本次改造后，运行时不应再存在这种通用入口。

应该拆成：

- 读 metadata
- 读 recent page
- 读 before/after 小窗口
- 读 runtime tail

而不是“读会话”。

## 5. 目标数据分层

目标分层应该是：

```text
业务层：
  overview / foreground / scheduler / archive / remote_im / task

读取层：
  conversation_metadata_reader
  conversation_recent_page_reader
  conversation_window_reader
  conversation_runtime_reader

存储层：
  chat_index
  conversation meta
  message_store recent page
  message_store blocks / idx
```

禁止重新出现这种依赖方向：

```text
业务层 -> 完整 Conversation
业务层 -> cached_conversations
overview -> state_read_conversation_cached
scheduler -> state_read_conversation_cached
```

## 6. 硬规则

本次改造后，生产代码中不允许继续出现以下语义：

```text
cached_conversations
HashMap<String, Conversation>
metadata cache 中存 Conversation
overview 遍历 chat_index 后逐个读完整会话
调度前预读完整会话
切会话时加载完整会话
```

允许存在的读取语义只有：

```text
read_conversation_metadata(...)
read_recent_messages_page(...)
read_messages_before(...)
read_messages_after(...)
read_runtime_tail(...)
read_summary_source_message(...)
```

## 7. 最小重构范围

第一阶段只做“把错误边界拆掉”，不追求一次性美化全部命名。

第一阶段至少覆盖：

- `runtime_state`：移除整会话常驻缓存定义
- `runtime_cache`：删除/废弃整会话缓存读入口
- `conversation_service/reads`：overview/list 改为只读 metadata + recent page
- `conversation_snapshot_api`：前台概览刷新不再触发全量正文加载
- 调度链路：改为只消费当前会话尾部读取接口

## 8. 非目标

这次不做：

- 前端协议大改
- UI 交互改版
- message_store 存储格式重写
- 一次性把所有历史模块全部重命名
- 引入 SQLite 或新数据库

这次只做一件事：

- **把“完整会话进入运行时”这条错误路径彻底切断**

## 9. 验收标准

改造完成后，必须满足以下验收条件：

### 9.1 运行时结构验收

- 不再存在 `cached_conversations`
- 不再存在以 `Conversation` 为 value 的 metadata cache
- overview / list / foreground refresh 不再调用整会话读取入口

### 9.2 行为验收

- 打开应用后，仅浏览会话列表，不会把全量会话正文装入内存
- 切换会话时，只读取最近消息页和 runtime 投影
- 调度执行时，只读取当前会话尾部消息窗口
- 归档、摘要、未读数刷新都不需要完整会话

### 9.3 内存验收

- `cachedConversations` 类统计项归零或被移除
- `cachedConversationMetadata` 不再与整会话体积同量级
- `message_store block cache` 仍只保留最后少量块

## 10. 实施原则

实施时必须遵守：

1. 先删错误抽象，再补正确读取接口，不能继续在旧抽象上打补丁。
2. 先保证 overview/list 不再全量读正文，再收口调度链路。
3. 任何遇到“这里拿个 Conversation 最方便”的地方，都按设计错误处理，不允许继续妥协。
4. 如果某个现有接口签名要求返回 `Conversation`，优先视为接口设计错误并拆分，而不是继续兼容完整对象。

## 11. 最终判断

这不是一次性能优化，也不是缓存微调。

这是一次**运行时数据边界纠偏**：

- 过去的错误：把“完整会话”当成默认运行对象
- 正确的实现：只允许 metadata、尾部消息窗口、块缓存、运行时投影进入内存

后续所有实现都必须服从这条边界，不能再退回“先拿整会话再说”的旧思路。
