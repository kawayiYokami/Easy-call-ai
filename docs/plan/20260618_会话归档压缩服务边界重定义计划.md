# 20260618 会话归档压缩服务边界重定义计划

## 1. 结论

这次先不讨论“怎么改”，只钉死产品语义、服务边界、接口边界、数据边界和验收口径。

本次要确认的不是实现手法，而是以下硬边界：

- 归档会话与压缩会话是两个完全独立的内置功能。
- 两者都属于会话服务的正式能力，不再共享同一个功能模块。
- 两者对外只暴露按 `conversationId` 调用的接口。
- 两者完成后只返回成功或失败，不再暴露会话选择器、运行态补参或混合语义入参。
- 压缩会话的职责是“基于目标会话形成新的摘要块与摘要消息”，不是“顺手走一遍归档链路的轻量版”。

## 2. 背景

当前实现已经偏离这次要的目标边界，主要体现在四点：

1. 归档和压缩仍然放在同一个模块语义下。
2. 压缩入口不是纯 `conversationId` 接口，而是仍然接受带 `agentId`、`apiConfigId` 的复合选择器。
3. 压缩逻辑当前依赖整会话语义，不是一个明确的“对目标会话执行压缩”服务动作。
4. 归档与压缩的职责边界仍然混在同一条 SummaryContext 叙事里，导致模块边界、调用边界、返回边界都不够硬。

这次计划的目标，是先把“应该是什么”写死，再决定“怎么落地”。

## 3. 本次要钉死的需求

### 3.1 归档会话

归档会话是会话服务的一个独立内置功能。

它必须满足：

1. 只接受 `conversationId`。
2. 自己根据 `conversationId` 解析目标会话。
3. 自己完成归档所需的读取、摘要、记忆处理、落盘与状态收敛。
4. 对外只返回成功或失败。

### 3.2 压缩会话

压缩会话是会话服务的另一个独立内置功能。

它必须满足：

1. 只接受 `conversationId`。
2. 自己根据 `conversationId` 解析目标会话。
3. 自己完成压缩所需的块读取、摘要、记忆处理、保留对话采集、新块生成与落盘。
4. 对外只返回成功或失败。

### 3.3 两者关系

两者都可以调用会话服务内部已有的通用能力，但不允许因此被定义为“共享模块”或“同一条功能链路的两个场景”。

这里要钉死的是：

1. 归档和压缩都是会话服务自己的内置功能。
2. 会话服务内部已有的读写、落盘、模型调用、记忆写入等方法，仍然只是会话服务内部方法。
3. 这些内部方法不能成为“归档压缩其实还是一个功能”的理由。

不允许出现的内容包括：

1. 同一个“归档压缩合并模块”。
2. 同一个对外命令入口。
3. 同一个上层功能语义对象。
4. 通过场景分支把压缩和归档塞进同一条主流程。

## 4. 压缩会话的目标语义

压缩会话的正式目标流程定义如下。

### 4.1 输入

输入只有一个：

- `conversationId`

压缩服务不得要求调用方额外提供：

- `agentId`
- `departmentId`
- `apiConfigId`
- `session`
- `targetConversationId`
- 任何“如果不传就自动猜”的混合选择器字段

### 4.2 读取目标块

压缩服务首先必须根据 `conversationId` 读取目标会话的最后一个块。

这里的“最后一个块”是压缩语义的主对象。

但这不等于压缩阶段只能看到最后一个块内的所有信息源。

本次明确区分两个概念：

1. 压缩主对象
   - 最后一个块。
2. 压缩保留对话采集来源
   - 从整会话尾部向前按规则采集。

也就是说：

- “最后一个块”负责摘要与记忆主任务。
- “整会话尾部向前采集”负责补足摘要消息中的保留对话。

### 4.3 生成摘要与记忆

压缩服务必须基于目标会话的最后一个块生成：

1. 压缩摘要。
2. 相关记忆结果。

这里要钉死的边界是：

- 摘要和记忆的主分析输入是最后一个块。
- 不是把整会话直接当作压缩摘要输入。

### 4.4 采集摘要保留对话

压缩服务在生成完摘要与记忆后，必须根据 `conversationId`，从目标会话“最后一条消息的正文”开始向前逐条采集摘要保留对话。

这里的要求是：

1. 采集对象是消息正文。
2. 采集方向是从新到旧向前逐条收集。
3. 采集目标是形成摘要消息中的“保留对话”部分。

本次只钉死语义，不提前规定：

1. token 预算是多少。
2. 字符预算是多少。
3. 是否带 role 标识。
4. 是否允许截断单条正文。

这些属于后续实现策略，不在本计划中先定。

### 4.5 生成新的摘要消息与新块

压缩服务完成摘要、记忆、保留对话采集后，必须：

1. 生成新的摘要消息。
2. 生成新的块。
3. 使该摘要消息成为新块中的第一条消息。

这是压缩服务的硬结果，不允许退化为：

1. 仅向旧块尾部追加一条整理消息。
2. 仅更新会话 `summary` 字段而不形成新块。
3. 借由“消息仓库自动决定是否新开块”的偶然副作用来满足语义。

也就是说，最终语义必须是：

- 压缩操作显式产出一个新的摘要块。

### 4.6 返回

压缩服务完成后，只向调用方返回：

1. 成功
2. 失败

本次先不定义最终返回结构是布尔值、空结果还是简单 `Result<()>`。

这里只钉死一件事：

- 返回值不承载上层功能语义，不再回传一组混合业务信息来让调用方自行解释。

## 5. 归档会话的目标语义

归档会话本次不重写详细业务步骤，但要先钉死它与压缩会话的关系边界。

### 5.1 输入边界

归档会话只接受：

- `conversationId`

### 5.2 功能边界

归档会话负责的是：

1. 对目标会话做正式归档。
2. 完成归档摘要与归档相关记忆处理。
3. 完成归档状态落盘。

归档会话不应再承担：

1. 对外兼任压缩会话入口。
2. 为压缩会话提供上层主流程壳。
3. 以“场景参数切换”的方式兼容压缩语义。

### 5.3 返回边界

归档会话对外只返回成功或失败。

## 6. 模块边界

### 6.1 必须独立

归档模块与压缩模块必须完全独立。

这里的“完全独立”指的是：

1. 独立的功能模块文件或功能目录。
2. 独立的服务入口。
3. 独立的上层语义命名。
4. 独立的测试组织。

### 6.2 不允许的形态

本次明确不接受以下形态：

1. 一个 `archive_pipeline` 里靠参数分支区分归档和压缩。
2. 一个 `summary_context_pipeline` 里塞两个场景枚举再分别处理。
3. 一个共享 `ForceArchiveResult` 或同类混合结果对象同时服务两个功能。
4. 一个入口名义上是压缩，内部实质还是调用归档模块中的通用主流程。

### 6.3 会话服务内部通用方法边界

本次允许复用的，只能是会话服务内部已经存在或后续补齐的通用方法，例如：

1. 消息仓库读写方法。
2. 会话元数据读写方法。
3. 块读取方法。
4. 模型调用方法。
5. 记忆存储方法。
6. 通用日志方法。

但这些都只是会话服务内部方法，不构成新的“共享功能层”，也不改变以下事实：

1. 归档是独立功能。
2. 压缩是独立功能。
3. 两者不能再被组织成同一个业务模块。

## 7. 接口边界

### 7.1 对外接口数量

会话服务对外只提供两个正式接口：

1. `archiveConversation(conversationId)`
2. `compactConversation(conversationId)`

此处函数名只是语义表达，不代表最终命名已经确定。

本次钉死的是接口数与接口意图，不是最终代码命名。

### 7.2 接口输入边界

两个接口都只接受：

- `conversationId`

### 7.3 接口输出边界

两个接口都只返回：

- 成功或失败

本次明确不再接受以下对外接口模式：

1. 传 `session selector`
2. 传 `agentId + conversationId`
3. 传 `apiConfigId + conversationId`
4. 返回大量过程性字段让前端或调用方二次解释

## 8. 数据边界

### 8.1 压缩输入数据边界

压缩操作允许读取的数据边界如下：

1. 目标会话最后一个块
2. 目标会话尾部消息正文序列
3. 压缩流程所需的记忆上下文

### 8.2 压缩输出数据边界

压缩操作必须产生的数据结果如下：

1. 新摘要消息
2. 新摘要块
3. 记忆写回结果

### 8.3 归档输出数据边界

归档操作必须产生的数据结果如下：

1. 归档状态变化
2. 归档摘要结果
3. 归档相关记忆写回结果

## 9. 非目标

本计划明确不提前决定以下内容：

1. 模块文件最终怎么拆。
2. 哪些旧函数搬到哪里。
3. 具体 prompt 文本怎么写。
4. 记忆 JSON 结构是否顺手调整。
5. 前端按钮、弹窗、文案是否同步重命名。
6. 返回结构最终采用哪一种 Rust 类型。
7. 迁移期间是否保留兼容层以及兼容多久。
8. 是否顺手清理当前所有 SummaryContext 历史命名。

这些都属于后续“怎么改”的话题，不属于本次计划。

## 10. 验收标准

本次需求与边界确认后，后续实现必须满足以下验收标准。

### 10.1 接口验收

1. 归档接口只接受 `conversationId`。
2. 压缩接口只接受 `conversationId`。
3. 两个接口都不再要求补传 `agentId`、`session`、`apiConfigId`。

### 10.2 模块验收

1. 归档与压缩不再位于同一功能模块语义下。
2. 两者不再通过同一主流程配合场景参数来复用。

### 10.3 压缩语义验收

1. 压缩会先定位目标会话最后一个块。
2. 摘要与记忆主分析输入来自最后一个块。
3. 保留对话从目标会话尾部正文向前逐条采集。
4. 压缩结果会显式形成新的摘要块。
5. 摘要消息是该新块中的第一条消息。

### 10.4 归档语义验收

1. 归档是独立功能，不再依附压缩模块。
2. 归档只按 `conversationId` 驱动完整流程。

## 11. 现状与目标的差异结论

基于当前讨论，本计划先确认以下事实：

1. 当前现状不满足本计划要求。
2. 当前压缩与归档的模块边界不符合要求。
3. 当前压缩接口边界不符合要求。
4. 当前压缩流程的主对象边界不符合要求。
5. 后续实现应以本计划为准，而不是以当前实现的兼容形状为准。

## 12. 待确认项

以下问题不影响本计划成立，但建议在进入实现前由你拍板：

1. 压缩后的旧块是否保留完整原文，仅通过新摘要块建立“新的上下文起点”，还是需要同时对旧块做瘦身标记。
2. “保留对话”是否只采集正文文本，还是允许保留必要的结构化附加信息。
3. 归档与压缩的成功返回是否统一成同一种极简结果类型。
4. 压缩与归档是否都要禁止处理系统通知会话、联系人会话、委托会话，还是分别定义自己的允许范围。
