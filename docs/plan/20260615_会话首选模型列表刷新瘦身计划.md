# 会话首选模型列表刷新瘦身计划

## 背景

当前“切换会话首选模型”会把模型信息混在会话列表概览更新链路中处理。用户只是在当前打开的会话输入框切换模型，但后端会重新生成并广播未归档会话概览，前端多个窗口收到后可能触发列表、归档、远程联系人会话等刷新。

典型日志表现：

- `[会话模型] 开始/完成，任务=切换会话首选模型`
- `[会话概览] 开始/完成，任务=推送未归档会话概览`
- `[远程IM][联系人会话][列表] 开始/完成`
- `[远程IM][联系人会话][块分页] 开始/完成`
- `[会话锁] 持有完成: task=...reads.rs / archive.rs`

这说明“模型字段变化”被当成“会话列表整体变化”传播，导致大量与本次操作无关的读取和 UI 刷新。

## 问题定义

会话首选模型是“打开该会话并准备发送消息时才需要”的运行输入字段，不应该成为全局会话列表刷新理由。

当前设计的问题：

- 未打开的会话，前端不应该关心它的首选模型是什么。
- 会话列表概览携带/更新模型信息，会把一个会话的模型变化扩散成列表级全局事件。
- 归档窗口、远程联系人会话列表等不展示也不依赖会话模型，却可能因为同一个概览事件被动刷新。
- 后端为模型切换重新收集未归档会话概览，会增加会话锁持有和不必要的读侧压力。
- 前端事件语义过粗，`conversation-overview-updated` 同时承担结构变化、排序变化、元信息变化等多种职责。

## 目标

- 切换当前会话模型时，只更新当前会话的发送运行态，不触发全局会话列表刷新。
- 未打开的会话不向前端主动同步首选模型字段。
- 会话列表概览不再因为首选模型变化而整体广播。
- 归档窗口和远程联系人会话不因本地普通会话模型切换刷新。
- 保留必要一致性：切换后当前输入框立即显示新模型，发送消息时使用新模型，失败时可回滚。

## 非目标

- 不重做会话列表 UI。
- 不改变部门默认模型、角色模型解析、模型可用性校验规则。
- 不改变归档窗口本身的数据加载策略，只避免它被模型切换误触发。
- 不处理远程联系人会话自身的模型选择策略。

## 设计方向

### 1. 拆分“当前会话运行态模型”和“列表概览”

当前打开会话的首选模型应由当前会话状态维护，例如：

- `currentChatConversationId`
- `currentChatPreferredApiConfigId`
- 发送前读取的 active api config 派生状态

会话列表概览只保留列表展示和路由所需字段，例如标题、时间、置顶、运行态、未读、部门/人格摘要等。首选模型字段不作为列表刷新依据。

### 2. 后端切模型命令不广播整包概览

`set_conversation_preferred_model` 的理想行为：

- 校验会话 ID 和模型 ID。
- 写入会话元信息。
- 返回 `{ conversationId, preferredApiConfigId }` 给调用方。
- 不调用 `refresh_unarchived_conversation_overview_payload`。
- 不 emit `easy-call:conversation-overview-updated`。

如确实需要跨窗口同步当前打开的同一会话，可新增窄事件，例如：

- `easy-call:conversation-preferred-model-updated`
- payload 只包含 `conversationId` 和 `preferredApiConfigId`
- 只有打开该会话的聊天窗口消费；列表、归档、远程联系人窗口忽略。

### 3. 前端只让当前会话关心模型变化

当前会话输入框切换模型时：

- 先乐观更新 `currentChatPreferredApiConfigId`。
- 调用后端保存。
- 保存失败时只回滚当前会话的模型 ref。
- 不刷新 `unarchivedConversations`。
- 不刷新 `remoteImContactConversations`。
- 不请求当前会话快照，除非当前会话 ID 已变化或运行态需要恢复。

其他窗口收到窄事件时：

- 如果自己当前打开的会话 ID 不匹配，直接忽略。
- 如果匹配，只更新当前会话模型 ref。
- 不触发会话列表或归档加载。

### 4. 收窄归档窗口监听

归档窗口不展示模型，因此模型切换不应触发：

- `loadArchives()`
- `remote_im_list_contact_conversations`
- `remote_im_get_contact_conversation_block_page`
- `list_archives`

即便保留 `conversation-overview-updated` 监听，也应只处理真正会影响归档窗口当前视图的数据变化；模型变化不属于归档窗口关心范围。

## 实施步骤

1. 梳理会话列表概览类型，确认首选模型字段是否仍被列表 UI 使用。
2. 修改 `set_conversation_preferred_model`，移除整包未归档概览刷新和广播。
3. 如需要跨窗口同步，新增 `conversation-preferred-model-updated` 窄事件。
4. 前端聊天窗口监听窄事件时，只在 `conversationId === currentChatConversationId` 时更新当前模型 ref。
5. 移除模型切换后所有 `refreshChatUnarchivedConversations()`、`loadArchives()`、远程联系人列表刷新路径。
6. 审查归档窗口 `conversation-overview-updated` 监听，避免用 `loadArchives()` 响应非归档数据变化。
7. 保留关键错误日志，删除正常模型切换的 info 级链路日志。

## 验收标准

切换当前会话模型时，日志中只应出现：

- 后端切换会话模型开始/完成日志，或保存失败错误日志。
- 不应出现 `[会话概览] 推送未归档会话概览`。
- 不应出现 `[远程IM][联系人会话][列表]`。
- 不应出现 `[远程IM][联系人会话][块分页]`。
- 不应出现由归档窗口触发的 `list_archives` / `archive.rs` 读锁日志。

功能行为：

- 当前输入框模型立即切换。
- 切换后发送消息使用新模型。
- 保存失败时当前输入框回滚到旧模型，并提示错误。
- 其他未打开会话不因模型变化更新或刷新。
- 归档窗口打开时，切换聊天窗口模型不会导致归档窗口列表闪动或远程联系人会话重载。

## 风险点

- 如果某些列表项当前依赖 `preferredApiConfigId` 展示模型标签，移除列表级同步前需要先去掉该 UI 依赖，或改成仅打开会话时加载。
- 多聊天窗口同时打开同一会话时，需要窄事件同步当前会话模型，否则另一个窗口输入框可能暂时显示旧值。
- 发送链路必须以当前会话状态或后端会话元信息为准，不能依赖过期的列表概览字段。

## 待确认

- 会话列表是否彻底不展示模型信息。
- 是否允许多个窗口同时打开同一会话；如果允许，需要实现窄事件同步。
- VS Code sidebar 是否也需要同样的窄事件语义，避免它继续用整包概览同步模型变化。
