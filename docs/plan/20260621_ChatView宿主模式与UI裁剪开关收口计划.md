# 20260621 ChatView 宿主模式与 UI 裁剪开关收口计划

## 一、目标摘要

本计划用于记录 `ChatView` 内部 `sidebarMode` / `bridgeMode` 的现状、问题边界与后续收口方向，但**本轮只写计划，不进入实现**。

当前代码表现正常，最近这一轮聊天滚动、加载更多、上推动画也已经稳定。  
因此这次不以“顺手清理历史命名”为目标，而是先把边界记清楚，避免后续在没有真实收益的情况下贸然改动稳定链路。

本计划的核心结论如下：

- `sidebarMode` 还在被使用，但已经不再代表“VS Code 宿主环境”。
- `bridgeMode` 更接近“当前运行在桥接宿主里”的环境语义。
- `VS Code sidebar` 当前复用的是同一个 `ChatView`，不是另一套聊天实现。
- 现阶段没有证据表明这两个开关的混用已经导致真实用户问题。
- 因此本轮结论是：**先搁置，不改实现，只保留后续收口方案。**

---

## 二、当前事实

### 1. ChatView 是共享主实现

- 桌面聊天主链路使用 `src/features/chat/views/ChatView.vue`
- VS Code 侧边栏包装层 `src/features/sidebar/views/ChatViewWrapper.vue` 也是直接渲染同一个 `ChatView`
- 最近完成的聊天滚动修复、顶部加载更多稳定性修复，VS Code 侧边栏会一起复用这一套主逻辑

这意味着后续任何模式变量重命名或收口，都不是“改 sidebar 小壳子”，而是在触碰共享聊天主链路。

### 2. sidebarMode 的真实语义已经变窄

当前 `sidebarMode` 仍然被若干逻辑使用，但它的作用更接近：

- 控制某些 UI 是否裁剪
- 控制某些弹窗/面板是否挂载
- 控制某些高阶操作是否显示或启用

它已经不再适合被理解为：

- 是否运行在 VS Code 侧边栏
- 是否运行在 webview
- 是否运行在桥接宿主

### 3. bridgeMode 的真实语义更像宿主环境

当前 `bridgeMode` 更接近：

- 是否运行在桥接宿主中
- 是否通过 `bridgeRequest` 间接调用能力
- 是否不能直接依赖桌面环境提供的原生窗口/文件/能力入口

从现状看，`bridgeMode` 主要服务于 VS Code sidebar / webview 这类桥接容器。

### 4. VS Code 当前并不依赖 sidebarMode 才能禁用功能

VS Code wrapper 现在即使传 `sidebarMode = false`，很多功能仍然会被禁用或失效，原因包括：

- wrapper 直接传入裁剪后的数据
- wrapper 将部分事件接成 `noop`
- `bridgeMode` 和宿主能力边界天然限制部分行为
- 某些入口同时受多个条件控制

因此当前功能限制已经不是“只靠 sidebarMode 一把梭”的结构。

---

## 三、当前不改的原因

### 1. 没有真实故障正在发生

目前观察到的是命名与语义不够整洁，而不是运行时异常、逻辑错误或用户可感知 bug。

最近已经验证正常的内容包括：

- 发送后的上推动画
- 顶部加载更多稳定性
- 消息虚拟列表与分组删除后的滚动行为

在这种时点继续抽象变量语义，风险高于收益。

### 2. 这类改动会触碰共享聊天主链路

`ChatView` 同时服务：

- 桌面聊天窗口
- VS Code 侧边栏包装层
- 可能的其他嵌入式桥接视图

即使只是“把变量改名成更对的名字”，也很容易在以下地方引入副作用：

- 条件渲染
- toolbar 菜单显示
- 代码审查 / 委托 / 文件阅读等侧边面板挂载
- bridge 宿主下的本地文件与链接行为
- 滚动、测量、布局相关的条件分支

### 3. 现在缺的是边界盘点，不是立即重构

目前更缺的是回答这几个问题：

1. `sidebarMode` 还有哪些真实调用点？
2. 这些调用点是在表达“宿主环境”，还是在表达“UI裁剪”？
3. 哪些应该改到 `bridgeMode`？
4. 哪些应该重命名为新的 UI 开关？
5. 哪些实际上已经可以删除？

在这些问题没盘清之前，直接改实现只会把稳定代码重新打散。

## 四、后续如果要做，应该怎么收口

### 1. 先分离两个概念

后续如果进入实现，必须先把两个概念拆开：

- 宿主环境判断
  - 是否运行在桥接容器中
  - 是否依赖 `bridgeRequest`
  - 是否受宿主能力边界限制
- UI 裁剪判断
  - 是否显示精简版聊天界面
  - 是否关闭某些高阶入口
  - 是否不挂载部分面板或弹窗

不允许继续让一个变量同时承担这两层含义。

### 2. 对每个 sidebarMode 使用点逐个归类

后续实现前，应把所有 `sidebarMode` 分支逐项归为三类：

1. 应改为 `bridgeMode`
2. 应改为新的 UI 裁剪开关
3. 已无必要，直接删除

只有归类完成后，才允许开始实际代码替换。

### 3. bridgeMode 不应被滥用成“万能禁用开关”

后续就算引入更多 `bridgeMode` 判断，也只能用于“宿主环境差异”：

- bridge 请求方式
- 本地文件打开方式
- 窗口能力差异
- 原生能力不可用时的降级路径

不能把所有“我不想在这个界面显示”的东西都塞到 `bridgeMode` 下。

### 4. 如果 UI 裁剪需求已经不存在，应优先删除而不是重命名

后续如果确认：

- 没有任何入口还需要一个真正的“精简版聊天 UI”
- VS Code 也坚持复用完整 ChatView

那么优先方案不应是“把 `sidebarMode` 改名”，而应是：

- 直接删除这一层 UI 裁剪开关
- 把保留下来的必要限制挪到更具体的条件上

## 五、后续触发条件

只有在满足以下任一条件时，才建议重新启动这份计划：

1. `sidebarMode` / `bridgeMode` 的混用已经导致真实 bug
2. 需要新增一个新的 bridge 宿主，现有语义已经无法扩展
3. 需要做明显的聊天 UI 分叉，当前模式命名已阻碍实现
4. 后续重构已经必须触碰 `ChatView` 主结构，顺手清理这层变量语义的边际成本明显变低

如果只是“看到名字不顺眼”，不建议启动。

---

## 六、实施前检查清单

未来如果真的进入实现阶段，先做以下检查：

1. 全局列出 `sidebarMode` 使用点并逐项归类
2. 全局列出 `bridgeMode` 使用点并确认是否全都在表达宿主环境
3. 确认 VS Code wrapper 是否仍然需要 `sidebarMode = false`
4. 确认是否还有任何入口真正需要“精简聊天 UI”
5. 明确本轮目标是“重命名”“删除变量”还是“拆成两个新变量”
6. 先写一份更新后的执行计划，再进入实现

## 七、本计划的当前结论

本计划当前不进入实现，先作为冻结记录保留。

现阶段以“行为稳定优先”为准：

- 不为了命名洁癖打扰已经稳定的聊天滚动链路
- 不为了语义整洁去重动 VS Code 侧边栏共享主视图
- 不在没有真实问题和明确收益时重构模式变量

后续如果出现真实需求，再以本计划为入口继续推进。
