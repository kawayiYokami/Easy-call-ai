# 20260609 调度压缩流式边界修复计划

## 背景

调度流式过程中触发上下文压缩时，后端会先结束当前调度片段并把流式草稿落盘为 assistant checkpoint，然后执行压缩并重启调度。当前前端有时临时只显示“压缩消息 + 新流式草稿”，少了压缩前刚落盘的 assistant checkpoint；刷新后又能看到，说明后端持久化是完整的，前端事件边界不完整。

## 目标

1. 压缩边界前的流式草稿一旦落盘，前端必须把它视为正式 assistant 消息。
2. 压缩完成后前端显示顺序必须稳定为：`assistant checkpoint -> 压缩消息 -> 新流式草稿`。
3. 压缩后内部重启调度时，后端必须显式通知前端新一轮 `round_started`，不能只依赖首个 delta 触发重绑。
4. 刷新不应成为恢复正确显示的必要条件。

## 方案

1. 后端在工具续调压缩 checkpoint 落盘后，把 assistant checkpoint 保存到本轮自动压缩上下文。
2. `run_context_compaction_pipeline` 支持接收“压缩边界前置消息”，并在 `compaction history_flushed` 中按顺序发送 `checkpoint assistant message + compression message`。
3. `send_chat_message_inner` 在压缩后 `continue 'dispatch` 之前，显式重置流式运行缓存并发送新的 `round_started`，使前端明确进入新一轮等待/流式状态。
4. 前端沿用现有 `history_flushed` 合并和 `round_started` 处理，不引入 UI 层假消息补丁。

## 验证

1. 运行相关 Rust 检查或定向测试，覆盖压缩 flush payload 顺序。
2. 运行前端类型检查，确保事件字段变更不破坏 TS。
3. 检查 diff，避免引入无关改动。
